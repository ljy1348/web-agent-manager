# 실험실 다분야·다공급자 확장 기획 (v3 · 합의안)

`docs/agent-lab.md`의 후속 기획이다. 구현 전 단계이며 Grok과의 토론으로 확정한다.

> v1 → v2: TaskProfile 추상화를 접고, 오탐 채점을 F1에서 사전식 순서로, ground truth 시작점을 합의형에서 회귀형·주입형으로 바꿨다. 역량 매트릭스는 코드 실측으로 정정했다.
> v2 → v3: 산출물 계약을 fixture에서 실험 필드로 옮기고, 심각도 가중치를 승자 규칙에서 빼고, 보고 예산 K를 고정값으로 못박고, 리팩터 노이즈를 `mustFind: false`가 아니라 제외로 바꿨다. 교차 스윕을 기본값에서 뺐다. **Grok과 2라운드 토론으로 합의된 내용이다.**

## 1. 요구

1. **분야 확장** — 코드 작성뿐 아니라 코드리뷰, 보안 등 여러 분야를 실험할 수 있어야 한다.
2. **축 확장** — 스킬셋 비교뿐 아니라 **AI 모델별**, **AI 공급자별**(Claude·GPT/Codex·Grok) 비교가 1급이어야 한다.

## 2. 현황 진단

### 2.1 이미 되는 것

- `ExperimentRuntimeConfig`에 `provider`·`model`·`reasoningEffort`가 있어 공급자·모델 비교는 데이터 모델상 가능하다. 부족한 것은 **자동 스윕**과 **통제 불가 축을 섞지 않는 규칙**이다.
- 세 Runtime이 **구조화 출력을 이미 지원한다** — Claude `--json-schema`, Grok `--json-schema`, Codex `--output-schema`(준비 단계의 `outputSchemaPath` 필요). `AgentRuntime` 계약에도 `outputSchema?`가 있다. **다만 하네스·experiment-service가 아직 넘기지 않는다.**
- rubric 평가 패킷(`BlindSubjectPacket`)은 `finalAnswer`와 `trackedDiff`를 함께 담는다.

### 2.2 막히는 것

**(A) 분야가 라벨이다.** `task_kind`는 DB 제약과 UI 태그이고, 실행을 바꾸는 곳은 `greenfield`에서 빈 Git 작업공간을 만드는 한 지점뿐이다.

**(B) 리뷰·감사의 탐지 품질을 잴 수 없다.** 여기서 구분이 필요하다.

| 질문 | 지금 가능한가 |
|---|---|
| "어느 쪽 리뷰 글이 더 나아 보이는가" | **가능** — `finalAnswer`가 패킷에 들어가므로 rubric·쌍대 비교가 돈다 |
| "누가 실제 결함을 찾았는가" | **불가능** — fixture에 정답이 없어 놓친 결함을 셀 수 없다 |

코드 변경이 없는 리뷰 run은 diff가 비고 자유 텍스트만 남는다. 그 상태의 쌍대 비교는 탐지 능력이 아니라 **문장의 그럴듯함**을 재는 것이다. 사용자 요구("코드리뷰·보안을 실험")는 탐지 품질로 읽히므로 정답 기반 채점이 필요하다.

**(C) 공급자 역량이 비대칭이다.** 아래 2.3 참조.

**(D) 모델 축이 수동이다.** variant를 손으로 하나씩 만들어야 한다.

### 2.3 공급자 역량 매트릭스 (코드 실측 기준)

v1의 표는 여러 곳이 틀렸다. 실제 구현은 이렇다.

| 축 | Codex | Claude | Grok |
|---|---|---|---|
| 스킬 on/off·선택 | 가능 | 가능 | **불가** — 끄거나 고정할 수단 없음. `mode: none`·`selected`·overlay를 저장·실행 전에 거부 |
| `maxTurns` | **불가** — 명시적으로 거부 | capability 탐지 후 사용 | native |
| 격리 방식 | OS 샌드박스 | **승인 모드**(`--permission-mode`) — OS 샌드박스가 아니다 | bwrap 있을 때만 OS 샌드박스 |
| 비용 상한 | WAM only | **native**(`--max-budget-usd`) + WAM | WAM only(`costBudgetEnforcement: "wam-only"`) |
| 구조화 출력 | `--output-schema`(파일 경로) | `--json-schema` | `--json-schema` |

핵심은 **모든 공급자에서 통제 가능한 축이 생각보다 적다**는 것이다. WAM `RuntimeBudgetPolicy`는 세 공급자에 공통으로 걸리므로 **공정한 바깥 울타리**가 된다. 차이는 절단 시점(Claude CLI가 더 일찍 자를 수 있음)이라 경고로 남기면 된다.

## 3. 제안

### 3.1 산출물 계약 — `task_kind`는 그대로 두고 축 하나만 추가

v1의 TaskProfile은 **상황 축**(`maintenance`/`greenfield`/`feature`/`security`)과 **산출물 계약**을 한 이름으로 묶어서 조합을 잃었다. 예를 들어 `security`는 "취약점을 고치는 과제"(기존)와 "취약점을 찾는 감사"(신규) 둘 다 될 수 있어야 한다.

`task_kind`를 유지하고 그 위에 **산출물 계약 하나**만 얹는다.

| 계약 | 산출물 | 채점 |
|---|---|---|
| `code_change` (현행) | 작업 트리 변경 | `testCommand` 종료 코드 → rubric → 쌍대 비교 |
| `finding_report` (신규) | 구조화 결함 목록 | ground truth 탐지 채점 (없으면 쌍대 비교만) |

조합 예시:

| `task_kind` | 계약 | 의미 |
|---|---|---|
| `security` | `code_change` | 기존 — 패치 + 재현 테스트 |
| `security` | `finding_report` | 신규 — 보안 감사 |
| `maintenance` | `finding_report` | 신규 — 코드리뷰 |
| `feature` | `code_change` | 기존 — 기능 추가 |

**코드리뷰와 보안 감사는 계약이 같다.** 채점기도 승자 규칙도 공유하고, 프로파일로 갈리는 것은 **분류 체계(taxonomy)와 프롬프트**뿐이다.

### 3.2 계약은 실험에, 정답은 fixture에

`outputContract`를 fixture에 두면 **같은 저장소·같은 정답으로 "고치기"와 "리뷰"를 돌릴 때 fixture가 복제된다.** 상황과 정답은 fixture에, 무엇을 만들지는 실험에 둔다. v1 TaskProfile을 접은 이유와 같다.

```
ExperimentFixtureInput                      // 정답과 묶인 것
  + reviewTarget: { baseCommit, headCommit } | null
  + findingTaxonomy: string | null          // 리뷰용/보안용 분류 체계 식별자
  + groundTruth: Array<{
      id, file, lineStart, lineEnd,         // 좌표는 검토 대상(부모) 트리 기준
      category, severity,                   // blocker | major | minor
      mustFind: boolean,
      rationale                             // 심사자 참고용. 에이전트에게는 숨김
    }> | null

experiments                                 // 무엇을 만들지
  + outputContract: "code_change" | "finding_report"   // task_kind 옆
```

### 3.3 산출물 형식 — native 구조화 출력이 1차

세 Runtime이 이미 `outputSchema`를 받으므로 `.wam/report.json` 파일 강제는 불필요하다.

- 1차: native 구조화 출력(`--json-schema` / `--output-schema`). 하네스가 스키마를 넘기도록 연결한다.
- 폴백: 지정 경로 파일. native 경로가 실패하는 공급자·버전을 위해 남긴다.

```text
{
  findings: [{
    file,          // 필수, 저장소 상대 POSIX 경로
    lineStart,     // 필수, 1-indexed
    lineEnd,       // 필수, lineStart 이상, inclusive
    category,      // 필수, 자유 문자열 → 동의어 표로 판정
    severity,      // 필수, blocker | major | minor
    title,         // 필수, 짧은 한 줄
    evidence?,     // 선택
    suggestion?    // 선택, 채점하지 않음
  }]
}
```

스키마에서 의도적으로 뺀 것:

- **`category`를 enum으로 잠그지 않는다.** 동의어를 스키마에서 거르면 탐지 실패가 형식 실패로 바뀐다.
- **`evidence`는 선택이다.** 필수로 둬도 "이 줄이 잘못되어 보입니다" 한 문장이면 통과해 "일단 신고"를 못 막고, 출력 토큰만 늘어 비용 축을 오염시킨다. 자동 매칭은 파일·라인·분류만 보므로 채점기가 읽지도 않는다. 재심·사람 확인·정답 없는 쌍대 비교에서 쓰고, 관찰 열로 "근거가 있는 보고 비율"만 남긴다.
- **`id`는 에이전트가 붙이지 않는다.** 매칭 id는 채점기가 부여한다.
- **`confidence` 필드를 두지 않는다.** 상위 K는 배열 순서로 판단한다.
- 빈 `findings: []`는 유효하다. 재현율 0으로 1번 축에서 지고 오탐 0으로 2번 축에서 이긴다.
- **형식 실패는 run 종료 이유가 아니다.** `suite-summary`는 `completed` run만 검사 통과율에 넣으므로, 종료 이유로 만들면 "JSON을 못 쓴 arm"이 비교에서 통째로 빠지거나 `runtime_error`와 섞인다. **run은 완료로 두고 산출물 상태를 `malformed`로 남기며, 형식 준수율은 별도 지표 열**로 관찰한다.

### 3.4 탐지 채점 — 사전식 순서, F1 금지

재현율만 보면 "의심스러운 것 전부 신고"가 이긴다. 그렇다고 F1으로 접으면 blocker 누락과 nit 오탐이 같은 무게가 되고, 단일 숫자가 사후 해석의 여지를 만든다.

기존 `suite-summary`와 같은 **사전 고정 사전식 순서**를 쓴다. 승자 결정은 이 순서만 따르고, precision·recall·F1은 **관찰 지표**로 표시한다.

1. **`mustFind` 재현율** — **비가중**
2. **오탐 부담** — 매칭되지 않은 보고 수
3. **위치 정확도**와 선택 항목
4. **비용**

1번을 비가중으로 두는 이유: `mustFind`가 이미 심각도 필터다. 사람이 blocker를 `mustFind: true`로 달았는데 승자 규칙에서 가중치를 한 번 더 곱하면 이중 계산이고, `blocker 3 / major 2 / minor 1`은 얕아서 **mustFind minor 3개가 blocker 1개를 상쇄한다.** 심각도 가중 합산(`Σ w·found − λ·FP`)은 표시용 점수에만 쓴다 — 승자 규칙에 넣으면 λ를 사후에 조정하게 된다.

**보고 예산 K = 20 고정.** 배열 앞에서부터 상위 20개만 채점하고 나머지는 무시한다(TP도 FP도 아니다). K의 역할은 오탐 처벌이 아니라 상한이다 — 살포는 2번 축에서 진다.

K를 정답 개수에 묶지 않는다(`max(10, |GT| × 2)` 같은 식은 **답지를 예산에 넣는 것**이다). fixture마다 허용 보고 수가 달라져 오탐 부담을 셀 사이에 비교할 수 없게 된다. 에이전트가 보는 것은 정답 개수가 아니라 검토 대상이다. 나중에 조정한다면 기준은 `reviewTarget`의 변경 줄 수이며, fixture LOC는 쓰지 않는다(큰 저장소의 한 줄 버그에 댓글 50개를 허용하게 된다).

### 3.5 매칭 규칙 — 자동 인정을 좁힌다

"같은 파일 + 라인 겹침 + 분류 일치"는 다음을 못 막는다.

- 파일 전체(1–500행)를 한 건으로 신고해 여러 정답을 흡수
- 긴 함수 안의 무관한 이슈가 겹침으로 매칭
- 모델마다 다른 분류 문자열(`correctness` vs `off-by-one`)

**자동 매칭 조건**

- 같은 파일
- 보고 span이 짧고(기본 40행 이하) 정답 span과 충분히 겹칠 것. **파일 전체 span은 자동 매칭 금지** — 단 파싱은 받는다. 파싱에서 막으면 "파일 단위 살포" 전략이 비교에서 사라져 버린다
- 분류는 완전 일치가 아니라 **동의어 표**로 판정

**재심 큐** — 파일만 같고 위치가 멀거나 분류가 표 밖이면 자동 부분 점수를 주지 않고 재심으로 보낸다. **첫 구현의 재심은 사람이 본다.** LLM 재심은 뒤로 미룬다 — 매칭 안 된 후보를 넘기면 심사가 관대해져 오탐이 정답으로 승격되기 쉽다. 도입하더라도 **파일이 같고 위치가 가까운 잔여 후보만** 넘기고, 기존처럼 블라인드·원장 보존·동일 계열 경고를 적용하며 사람이 `mustFind`를 뒤집을 수 있어야 한다.

### 3.6 공급자 비교 — 그룹 C 신설

기존 설계 1장 전제가 답을 준다. 공정함은 native 차이를 지우는 것이 아니라 **무엇을 통제하고 무엇을 평가 변수로 두는지 선언하는 것**이다.

| 평가 변수 | Grok | 규칙 |
|---|---|---|
| **공급자 제품 비교** (그룹 C, 신규) | 포함 | 스킬 `native`/`mode: all` 고정, 하네스 고정, `provider`·`model`만 변경 |
| **모델만 비교** (도구·스킬 통제) | 제외 | 스킬을 통제할 수 없으면 arm을 만들지 않는다 |
| **스킬 축** (기존 그룹 A) | 제외 | 현재 `parseExperimentVariantConfig`가 이미 거부 |

- 스킬 on/off를 공급자 비교에 섞으면 **거부**한다. 경고로 허용하지 않는다 — 통제하겠다고 선언하고 못 지키는 축은 결론을 못 쓰게 만든다.
- 경고로 남기는 것은 **선언된 native 차이**뿐이다(격리 방식, 비용 상한 절단 시점 등). 기존 "비교 유효성 경고"와 같다.
- "공급자별 다 테스트"는 그룹 C이며, **그룹 A 결과에 Grok을 끼워 넣은 결론은 내지 않는다.**

### 3.7 모델·공급자 스윕

- `sweep: { axis: "model" | "provider", values: [...] }`로 나머지 조건을 고정한 채 variant를 펼친다.
- 모델 목록은 `usage.cachedModelOptions(provider)`가 이미 공급자별로 들고 있다.
- **스윕은 비교 그룹을 새로 만드는 동작**이다. `isolated_overlay`의 `comparisonId`는 모델·추론 강도가 같아야 성립하므로, 모델 스윕을 스킬 비교 그룹에 펼치면 저장 단계에서 깨진다.
- 역량 매트릭스로 불가능한 arm은 **생성하지 않는다**.

**교차 스윕은 기본값이 아니다.** 공급자 3 × 모델 3 = 9 arm에 확증 표본 4회면 36 run이고, 실험은 전역 동시 1개라 벽시계가 먼저 막힌다. 반복을 3으로 낮추면 전부 잠정 등급이 된다 — `CONFIRMATION_MIN_SAMPLES = 4`는 3승 0패도 Wilson 구간이 겹친다는 이유로 고정된 값이라 낮출 수 없다. 기존 9-9의 단계 축소를 그대로 쓴다.

1. **기본은 두 개의 1차원 스윕이다.**
   - 그룹 C 공급자 스윕: 공급자당 **대표 모델 1개** × 1회. 공급자 간에는 모델 문자열을 같게 맞출 수 없으므로 대표 모델을 선언한다.

     **대표 모델은 실행 시점에 CLI 기본을 따라가면 안 된다.** 기존 9-4가 이미 금지한 사항이다 — 모델 칸이 비면 공급자가 기본 모델을 바꿀 때 같은 실험의 점수가 조용히 달라진다. 현재 Runtime도 `runtime.model`이 비면 `--model`을 넘기지 않고 CLI 기본에 맡긴다. 따라서 **스윕이 variant를 펼치는 시점에 "현재 기본"을 그때의 모델 문자열로 해석해 `runtime.model`에 저장한다.** 이후 재실행은 그 고정값을 쓰고, 사용자가 바꾸면 바꾼 문자열을 저장한다.
   - 모델 스윕: **한 공급자 안에서만.**
2. **스크리닝 1회**로 예산 초과·형식 실패가 잦은 arm을 떨군다.
3. **확증은 갈린 2~3 arm만 4회.** 9개 전부에 4회를 기본으로 두지 않는다.
4. 3×3 교차는 스크리닝에서 **순위가 뒤집힌 뒤에만** 한다.

"공급자별 다 테스트"는 공급자당 대표 모델 3 arm으로 충족된다. 교차는 상호작용을 볼 때의 추가 실험이다.

### 3.8 ground truth 구축 순서

합의형으로 시작하지 않는다. 순환(평가 대상이 정답 생성에 참여)만 문제가 아니라, **모든 모델이 놓친 결함은 정답에 들어가지 않아 "누가 어려운 버그를 찾는가"를 영원히 못 재는 편향**이 더 크다.

1. **코드리뷰 v1 = 회귀형** — 실제 수정 커밋의 부모를 검토 대상으로 주고, 수정 커밋의 파일·허크를 정답 후보로 쓴다. 사람은 분류·심각도·`mustFind`만 붙인다.

   **리팩터 노이즈는 `mustFind: false`가 아니라 정답에서 제외한다.** `mustFind: false`는 "있어도 되는 결함(nit)"용이다. 포매팅·변수명 정리·테스트 추가를 거기 넣으면 그 줄을 지적한 보고가 3번 축에서 점수를 받는다. 결함이 아니면 정답이 아니다.

   | 처리 | 대상 |
   |---|---|
   | 자동 제외 | `git diff -w`로 내용이 없는 허크, 바이너리, lockfile, **부모 트리에 없는 파일**(수정 커밋이 추가한 테스트·체인지로그) |
   | 사람이 판단 | 이름 변경, 메서드 추출, 주석만 변경 — 주석 오류가 실제 결함일 수 있고 추출이 버그 수정일 수 있어 자동 규칙으로 지우지 않는다 |

   사람은 남은 후보만 **mustFind / 선택 결함 / 제외**로 나눈다. 애매하면 제외가 기본이다.
2. **보안 감사 v1 = 주입형** — 유명 CVE·공개 저장소는 암기 오염 위험이 있다(기존 17장). 작은 fixture에 알려진 CWE를 심는 쪽이 첫 게이트로 낫다.
3. **합의형은 3순위** — 라벨 없는 실전 PR을 넣을 때만. 생성 패널과 피험 패널을 분리하고 `mustFind`는 사람이 확정한다. 한 모델만 지적한 항목은 자동 정답이 아니다.

### 3.9 정답 없는 실전 리뷰

별도 프로파일이 아니라 **같은 `finding_report`의 채점 경로 분기**로 둔다.

- ground truth 있음 → 탐지 채점
- 없음 → 쌍대 비교만. UI에 **"순위만 있고 탐지 주장은 불가"**를 명시한다. 안 그러면 주관적 승자를 탐지 능력으로 읽는다.

### 3.10 리뷰 중 코드를 고쳤을 때

`finding_report` 계약인데 에이전트가 diff까지 만든 경우다.

- **탐지 채점은 보고서만 본다.** diff에서 결함을 역추출하지 않는다. 고치기만 하고 보고가 비면 재현율 0이 맞다 — 구제하면 `finding_report`가 `code_change`로 새어 나간다.
- diff는 `hadNonEmptyDiff`와 diff 통계로 **관찰 열**에만 남긴다. 승자 규칙에 넣지 않는다.
- **계약 위반 감점은 하지 않는다.** 실무 리뷰어가 nit을 고치는 행동을 벌하는 셈이라 과하다.
- 통제는 채점이 아니라 **기본 샌드박스**로 한다. `finding_report` arm의 기본값은 `read-only`다. `workspace-write`도 허용하되 비교 유효성 경고만 단다(Claude 승인 모드는 쓰기를 완전히 막지 못하므로 경고가 현실적인 상한이다).

## 4. 구현 순서 (이 문서 범위 밖, 합의된 순서만 기록)

1. 산출물 계약(`code_change` | `finding_report`) + fixture `reviewTarget`·`groundTruth`
2. native `outputSchema`를 하네스에 연결 + 탐지 채점 단계(사전식 승자 규칙)
3. 역량 매트릭스를 생성 API 선언으로 승격 (거부 로직은 이미 있음)
4. 모델·공급자 스윕 — 비교 그룹을 새로 펼치고 스킬 `comparisonId`와 섞지 않음
5. 합의형 GT·LLM 재심 (첫 구현에서 제외 — 재심은 사람이 본다)

첫 PR 범위는 **1~2**면 충분하다.

## 5. 합의 결과 요약

Grok과 2라운드 토론으로 다음을 확정했다. 3라운드가 필요한 쟁점은 남지 않았다.

| 항목 | 결정 |
|---|---|
| 산출물 계약 | `code_change` \| `finding_report` 두 개. **실험 필드**(fixture 아님) |
| `evidence` | 선택. `category`는 자유 문자열(enum 금지) |
| 승자 1번 축 | **비가중** mustFind 재현율. 3/2/1 가중치는 표시용 |
| 보고 예산 | **K = 20 고정**, 상위 K만 채점. 정답 개수에 묶지 않음 |
| 리뷰 중 diff | 채점 무시 + 관찰 열. 기본 샌드박스 `read-only` |
| 리팩터 노이즈 | 정답에서 **제외**. 자동 제외는 공백·바이너리·lockfile·부모에 없는 파일뿐 |
| 교차 스윕 | 기본값 아님. 1차원 스윕 두 개 + 스크리닝 → 확증. **n=4 유지** |
| 대표 모델 | 스윕 시점에 문자열로 **해석해 저장**. 실행 시점 CLI 기본 추종 금지 |
| GT 구축 | 회귀형(리뷰) → 주입형(보안) → 합의형(마지막) |
| 재심 | 첫 구현은 사람. LLM 재심은 뒤로 |

## 6. 이 문서의 범위

기획까지다. 스키마 마이그레이션·Runtime 변경·UI는 포함하지 않는다.
